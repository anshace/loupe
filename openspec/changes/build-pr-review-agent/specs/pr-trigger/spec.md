# pr-trigger Specification

## Purpose

Detect pull request events and on-demand commands, authenticate their origin, and decide whether a review run should fire, so that reviews start automatically and only when appropriate.

## ADDED Requirements

### Requirement: Automatic review trigger on PR lifecycle events

The system SHALL start a review run when a pull request is opened, reopened, marked ready for review, or receives new commits (synchronize), without any manual invocation.

#### Scenario: PR opened

- **WHEN** a pull request is opened against a repository where the reviewer is enabled
- **THEN** a review run for that pull request's head commit SHALL begin

#### Scenario: New commits pushed to an open PR

- **WHEN** new commits are pushed to the branch of an open pull request (a synchronize event)
- **THEN** a review run SHALL begin for the updated head commit

#### Scenario: PR reopened or marked ready for review

- **WHEN** a previously closed pull request is reopened, or a draft pull request is marked ready for review
- **THEN** a review run SHALL begin for the current head commit

### Requirement: Draft and self-generated events are skipped

The system SHALL NOT start a review run for draft pull requests, and SHALL NOT start a review run in response to events generated by its own actions (its own comments, reviews, or reactions).

#### Scenario: Draft PR event received

- **WHEN** a pull request event arrives and the pull request is in draft state
- **THEN** no review run SHALL start
- **AND** no comments SHALL be posted to the pull request

#### Scenario: Event caused by the bot itself

- **WHEN** an event arrives whose actor is the reviewer's own identity
- **THEN** the event SHALL be discarded without starting a review run

### Requirement: Already-reviewed head commit is not re-reviewed

The system SHALL skip starting a review run when the pull request's current head commit has already been reviewed by the system, unless a review is explicitly requested on demand.

#### Scenario: Duplicate event for a reviewed commit

- **WHEN** a trigger event arrives for a pull request whose head commit matches the commit of the system's most recent completed review on that pull request
- **THEN** no new review run SHALL start

#### Scenario: Explicit on-demand request for a reviewed commit

- **WHEN** an authorized on-demand review command is issued for a pull request whose head commit was already reviewed
- **THEN** a review run SHALL start despite the prior review

### Requirement: On-demand review command gated to collaborators

The system SHALL support an on-demand review command (`/review`) issued as a pull request comment, and SHALL act on it only when the commenter is a collaborator on the repository. Commands from non-collaborators SHALL be ignored without any response.

#### Scenario: Collaborator issues /review

- **WHEN** a repository collaborator posts a comment beginning with `/review` on an open pull request
- **THEN** a review run SHALL start for the pull request's current head commit

#### Scenario: Non-collaborator issues /review

- **WHEN** a user who is not a repository collaborator posts a `/review` comment
- **THEN** the command SHALL be ignored
- **AND** no review run, comment, or reaction SHALL result

### Requirement: On-demand command acknowledgment

The system SHALL acknowledge an accepted on-demand review command with a visible reaction on the triggering comment before the review completes, so the requester knows the command was received.

#### Scenario: Accepted command is acknowledged

- **WHEN** an on-demand review command from a collaborator is accepted
- **THEN** the system SHALL add a reaction to the triggering comment before posting any review output

### Requirement: Webhook signature verification

The system SHALL verify the authenticity of every incoming webhook delivery against the shared webhook secret before processing its payload, and SHALL reject deliveries that are missing a signature or whose signature does not match, responding with an authentication error status and performing no further processing.

#### Scenario: Valid signed delivery

- **WHEN** a webhook delivery arrives with a signature that matches the payload under the configured secret
- **THEN** the payload SHALL be processed normally

#### Scenario: Missing or invalid signature

- **WHEN** a webhook delivery arrives with no signature header, or with a signature that does not match the payload
- **THEN** the delivery SHALL be rejected with an authentication error status
- **AND** no part of the payload SHALL be acted upon
